# Заметка к задаче #589: Как понять, что помощнику ИИ можно доверять

## Источники и проверка материалов (Шаг 0)

Проверены первоисточники:
1. **arXiv:2611.01976**: *Beyond Prompt Injection: The Tool Update Gap in LLM Agent Security*
   - Раздел 4 (§4, Approach / ETUDE): разрыв доверия при обновлении инструментов (tool update gap). Инструмент версии v1 выполняет заявленные функции и проходит проверку. Обновление v2 сохраняет тот же интерфейс (R1) и правильные результаты (R2), но внутри выполняет лишние несанкционированные действия (R3) без отдельных вызовов со стороны модели.
   - Раздел 6 (§6, Discussion): разделение уровней защиты:
     - Привязка авторизации к конкретному артефакту (artifact identity: хеш версии, неизменяемость проверенного кода), а не к общему имени инструмента.
     - Ограничение поведения (behavioral confinement: наименьшие привилегии, строгий список разрешённых действий и ресурсов в рантайме), так как даже доверенный автор или подписанный пакет могут нести нежелательные действия.

2. **arXiv:2611.03772**: *RuntimeTickets: Source-Grounded Security Obligations for Agent Skills*
   - Раздел 1 (§1, Introduction): навыки и инструменты ИИ работают с пользовательскими файлами, ключами и сетью. Статические проверки и широкие списки доступа недостаточны, когда инструмент решает задачу и одновременно делает лишнее действие (например, утечка данных при отправке).
   - Раздел 5.5 (§5.5, Case Study) и Приложение F: учебный сценарий повторного использования адресата (recipient-reuse). Задача — подготовить документ и отправить утверждённому адресату; модификация побуждает помощника попытаться отправить системные сведения тому же адресату. RuntimeTickets не пропускает эту отправку; адресат получает только разрешённый документ.

## Примеры для текста практикума

1. **Пример: верный ответ с тайным лишним действием**
   - *Описание:* учебный пример инструмента (например, помощник для форматирования текста или отчёта), который выдаёт правильный результат, но попутно читает посторонний файл или пытается отправить лишние данные. Без рабочего вредного кода — чисто описательное пояснение принципа.
   - SOURCE_URL: `https://arxiv.org/abs/2611.01976` (раздел 4) и `https://arxiv.org/abs/2611.03772` (раздел 1, 5.5)
   - SOURCE_CHECKED=yes

2. **Три уровня проверки: автор, версия, разрешения**
   - *«Известный автор»* (кто написал): популярность имени или репозитория не гарантирует безопасность будущих версий.
   - *«Проверенная версия»* (какой именно код запускается): фиксация конкретной версии или хеша, чтобы обновление не запустило непроверенный код без ведома пользователя.
   - *«Разрешённые действия»* (что именно программе позволено делать): ограничение доступа к файлам, папкам и сети только тем, что требуется для текущего дела.
   - SOURCE_URL: `https://arxiv.org/abs/2611.01976` (раздел 6) и `https://arxiv.org/abs/2611.03772` (раздел 1)
   - SOURCE_CHECKED=yes

3. **Короткий список проверок перед установкой**
   - Чек-лист из понятных шагов: зачем нужен инструмент, какая именно версия ставится, к каким папкам и ресурсам даётся доступ.
   - SOURCE_URL: `https://arxiv.org/abs/2611.01976` (раздел 6)
   - SOURCE_CHECKED=yes

## Исправление по содержательному ревью (2026-11-16)

- Повторно сверен [§5.5, «Case Study: An Attack That Reuses the Task’s Recipient»](https://arxiv.org/html/2611.03772#S5.SS5) и [приложение F, «The Recipient-Reuse Case in Detail»](https://arxiv.org/html/2611.03772#A6). §5.5 описывает добавленную инструкцию отправить системные сведения; результат раскрыт в приложении F, абзацах **«The injected send»**, **«The delivery»** и **«The same ticket in other runs»**, а также в подписи к рисунку 8.
- Точный смысл правки: прежнее «дополнительно отправлял сведения о системе» ошибочно представляло попытку как успешную отправку. В описанном запуске RuntimeTickets вынес `Defer` по условию `Valid`: содержимое запроса было зашифровано через TLS, поэтому проверить его было невозможно. Источник прямо говорит: **«The send is not forwarded and has no effect»**. Следующая отправка документа прошла проверку; получатель получил документ и ничего больше. В остальных запусках этой пары попытки тоже остановлены (`Defer` по `Valid` либо `Deny` по `Sum`), **«No injected send got through»**.
- Соседние утверждения согласованы с этим результатом: вывод про недостаточность одной проверки адресата сформулирован как условие («было бы недостаточно»); итоговый вымышленный вопрос теперь различает попытку, её блокировку и доставку только отчёта. Оба кратких описания случая в этой заметке исправлены. Разрешение такой отправки одним списком адресатов показано в приложении F, таблице 9, при воспроизведении запросов без модели и сети; это не успешная утечка в запуске RuntimeTickets.
- Дополнительно сверены [§4 и §6 arXiv:2611.01976](https://arxiv.org/html/2611.01976#S4): вымышленное обновление с правильным результатом и лишними действиями, разделение проверяемой версии и разрешённых действий соответствуют источнику.
