# Лаг скролла на сцене — разбор

Дата: 2026-08-29
Страница: `/?home=scene` → rewrite на `/gelateria` (`src/proxy.ts`)
Стенд: Chrome, macOS, окно 1710×909, DPR 2, `next dev` на `localhost:3000`

## Симптом

Со слов пользователя, три отдельных проявления:

1. Дёргается на самом первом скролле.
2. При движении вниз дёргает один раз, «около двери».
3. При возврате наверх дёргает **каждый раз**.

## Итог

Причина пунктов 2 и 3 — тень у `.scene-copy`:

```css
text-shadow: 0 0 0.55cqw var(--cream), 0 0 1.4cqw var(--cream),
  0 0 3cqw rgba(253, 252, 238, 0.85);
```

При ширине контейнера 1710px это 9, 24 и **51 пиксель** размытия, три слоя.
`text-shadow` размывает контуры всех глифов блока, а не прямоугольник вокруг
него. Пока блок отрисован, он лежит в растровых плитках и скролл бесплатный.
Уезжает далеко за кадр — Chrome плитки выбрасывает. Возвращается — размывается
заново, все три слоя.

Отсюда и асимметрия «вниз один раз, наверх каждый раз»: вниз блок героя уезжает
уже отрисованным, а пока идёшь дальше, его плитки вытесняются, и на обратном
пути он рисуется с нуля.

Работа идёт в растеризации, не в JS, поэтому её не видно ни в long tasks, ни в
Long Animation Frames — там всё было пусто (см. «Что сбивало с толку», п. 6).

**Правка:** `src/components/scene/scene.css` — два слоя по 3 и 9px вместо трёх
до 51px. То же самое в `.scene-legal` (было `0.6cqw`/`1.6cqw`). Радиус теперь в
пикселях, а не в `cqw`: в `cqw` стоимость отрисовки растёт вместе с шириной
окна, то есть на большом мониторе лагало сильнее, чем на маленьком.

Пункт 1 (первый скролл) отдельно не подтверждён замером — вероятно то же самое,
первая отрисовка блоков после срабатывания reveal.

## Как воспроизводится

Обязательна **глубокая** качель. Мелкая (300↔1200) не даёт ничего.

- Прокрутить 0 → 3200 → 0, полтора-два прохода.
- Провал ровно один на каждый проход наверх, 100–134мс.
- Координата: y ≈ 960–1100, **все провалы на движении вверх**.

Геометрия сходится: блок героя `GELATO / Маленькая школа ИИ.` занимает
y 667–1157, его нижний край пересекает верх окна как раз на 960–1160.

## Методика замера

Что делает харнесс (весь код жил в консоли вкладки, в репозиторий не попал):

- rAF-цикл, в каждом кадре пишем `[дельта, scrollY, направление]`.
- Скролл гоняем через `document.scrollingElement.scrollTop` — `window.scrollTo`
  Lenis перехватывает.
- Фаза = 2 цикла по 1500мс на плечо = 6 секунд. При 60 FPS это **357–360
  кадров**. Меньше — значит кадры терялись.
- Считаем кадры дольше 34мс (два интервала при 60 Гц).
- Перед замерами прогрев: пройти всё полотно с шагом 500px, чтобы догрузились
  `loading="lazy"` срезы, потом вернуться наверх и подождать ~2с.
- A/B-фазы подаются инъекцией `<style>` и патчем
  `CSSStyleDeclaration.prototype.setProperty` — React при этом жив.

Харнесс обязан сам перезапускаться по `visibilitychange` и рисовать результат
на странице (фиксированная плашка), иначе пользователю приходится уходить в
терминал и замер рушится.

## Решающий замер

Пять фаз подряд, React жив во всех:

| фаза | результат |
|---|---|
| базовая (три слоя, до 3cqw) | 133мс, 134мс |
| `text-shadow: none` | чисто, 357 кадров |
| текст скрыт (`visibility: hidden`) | чисто, 357 кадров |
| `text-shadow: 0 0 2px` | чисто, 357 кадров |
| базовая снова | 133мс, 100мс, 50мс |

Возврат провалов на пятой фазе — то, что отличает вывод от совпадения.

## Что снято с подозрения замером

Каждый пункт проверен A/B, а не рассуждением. Провалы оставались:

- срезы полотна — `display: none` на всех шести, 3 провала против 3;
- `.scene-nav` целиком и отдельно её `backdrop-filter`;
- `transition` у появляющегося текста (`[data-reveal]`);
- запись трековых переменных `--q`, `--lx`, `--ly`, `--rot`, `--lemon-*`;
- всё перечисленное разом;
- Lenis — пользователь подтвердил, что лагает и с ним, и без;
- `:hover` у двери, `drop-shadow` у вывески, бесконечные анимации.

## Что сбивало с толку

Ошибки методики, каждая давала ложный результат:

1. **Вкладка в фоне.** Chrome полностью останавливает rAF — замеры пустые или
   с дельтами в секунды. Лечится самозапуском по `visibilitychange` и выводом
   результата на саму страницу.
2. **Chrome Energy Saver.** При заряде ≤20% и без питания режет кадры до 30 FPS.
   Находка настоящая (медиана 33.3мс во всех девяти фазах, включая раздетую
   страницу), но к этой задаче отношения не имела. После включения питания —
   ровные 60 FPS, а ощущение лага осталось.
3. **`scrollTo` мимо Lenis.** Программный скролл идёт другим путём, чем колесо.
4. **`visibility: hidden` на картинках ничего не исключает** — скрытая картинка
   всё равно декодируется и растеризуется. Первый прогон «без полотна» был
   сделан так и не доказывал ничего. Нужен `display: none`.
5. **Пересборка `document.body.innerHTML` убивает React.** Обработчики
   отваливаются от новых узлов: умирает скролл-трек и не срабатывают reveal, то
   есть весь текст остаётся с `opacity: 0` и просто не рисуется. Страница
   становится «чистой» искусственно. Этот ложный результат заметил пользователь —
   по тому, что текст перестал появляться.
6. **LoAF с `buffered: true`** отдаёт записи прошлой сессии с потерянными
   деталями скриптов. На чистом прогоне картина подтвердилась: ноль long tasks,
   `scripts: []`, `blockingDuration: 0`, style+layout 0.2–0.6мс. То есть JS
   действительно ни при чём, вся работа в растеризации.

## Состояние на 2026-08-29

Правка задеплоена (коммит `ea5cd44`). Повторный замер после неё:
`computed` подтверждает `0px 0px 3px, 0px 0px 9px`, все пять фаз чистые,
357–359 кадров, ноль провалов.

**Открыто:** пользователь сообщает, что на localhost лаг остался, при этом
синтетическая качель 0↔3200 больше ничего не воспроизводит. Разница в способе
прокрутки: замер идёт программно и мимо Lenis, пользователь крутит колесом.
Следующий шаг — запись живого пользовательского скролла (rAF + long tasks +
LoAF, 45 секунд), харнесс подготовлен, до результата не доведён.

## Побочно: вес страницы

Отдельный вопрос «не жрёт ли сайт лишнего». Цифры сняты с настоящей прод-сборки
(в dev JS не минифицирован, там смотреть бессмысленно).

| | |
|---|---|
| JS + CSS страницы сцены | 312 КБ gzip, 16 чанков |
| Полотно, 6 срезов AVIF | ~500 КБ |
| Узлов в DOM | 178 |
| JS heap | 46 МБ |
| Сторонних доменов | 0 |

По байтам претензий нет. Дорого тут другое — пиксели:

- Срезы шириной 1600px показываются на 1710 CSS px при DPR 2, то есть браузеру
  нужно 3420 — **растяжение в 2.1 раза**. И мыло на ретине, и лишняя работа при
  каждой растеризации.
- Страница целиком — 3420×14974 физических пикселей, около 51 мегапикселя.
  Chrome не держит столько плиток и выбрасывает уехавшие.
- Шесть срезов в распакованном виде — **45 МБ** битмапов (1600×1169×4 × 6).

Это фон, на котором любая дорогая отрисовка бьёт особенно больно: чем чаще
плитки выбрасываются, тем чаще всё перерисовывается заново.
