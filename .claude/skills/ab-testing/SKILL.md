# A/B-тесты

Принцип: если для решения нет данных и нет однозначного здравого смысла, решение принимает
не агент, а пользователь по цифрам. Агент заводит тест, следит и делает сводку.

## Когда заводить тест

- Пользователь формулирует задачу словами «может быть», «не уверен», «как думаешь, лучше…».
- Есть 2+ разумных варианта и нельзя доказать, что один хуже.
- Изменение касается конверсии: CTA, цены, тексты, баннеры, порядок блоков, формы.

Когда НЕ заводить: баг (сломано → починить), явное нарушение UX (элемент закрывает контент
на всех устройствах и не несёт ценности), правка текста без цели конверсии, изменение в админке.
Если тест-кандидат смешан с багом — баг чинится сразу, спорная часть идёт в тест.

## Инфраструктура (уже есть)

- `src/lib/experiments.ts` — реестр `EXPERIMENTS`. Один объект на тест: key, hypothesis,
  variants (первый — контроль), startedAt, pathPrefix, primaryMetric, secondaryMetrics,
  minExposuresPerVariant, status, winner.
- `src/lib/experiments-client.ts` — хук `useExperiment(key, active)`. Возвращает вариант
  (`null` до монтирования). `active` = тестируемый элемент реально показан; только тогда уходит
  событие `experiment_exposed` и супер-свойство `$feature/<key>`.
- Жребий детерминированный по cookie `vid` (ставит `src/proxy.ts`), без хранения состояния.
- QA: `?exp_<key>=<variant>` принудительно включает вариант.
- `scripts/ab-report.mjs` — сводка из PostHog (HogQL). Ключ `POSTHOG_PERSONAL_API_KEY` в `.env.local`.
- События — только из `EVENTS` в `src/lib/analytics/events.ts`. Нужна новая метрика — добавь туда.

## Как завести тест

1. Сформулировать гипотезу одной фразой с числом «до» (из PostHog/Метрики) и ожидаемым эффектом.
2. Добавить запись в `EXPERIMENTS`. Контроль = текущее поведение. Обычно 2 варианта; больше —
   только если трафик > 200 экспозиций в день.
3. В компоненте: `const variant = useExperiment('<key>', shown)`. Пока `variant === null` на
   спорном месте ничего не рисовать, чтобы не мигал контроль.
4. Не ветвить весь компонент: разница между вариантами должна быть одной, иначе не понять,
   что сработало.
5. Проверить оба варианта через `?exp_<key>=…` в headless Chrome на 390px и на десктопе
   (рецепт в памяти `mobile-viewport-check`).
6. В ответе пользователю: что тестируем, какая метрика, сколько экспозиций нужно, когда смотреть.
7. Никаких UTM во внутренних ссылках — они перебивают атрибуцию источника.

## Как делать сводку

```
node scripts/ab-report.mjs            # все running
node scripts/ab-report.mjs <key>      # один тест
```

Сводка пользователю — таблица из скрипта плюс 3–5 предложений:
- достаточно ли данных (`minExposuresPerVariant`), если нет — когда будет при текущем трафике;
- что говорит главная метрика и вероятность P(лучше контроля);
- не сломались ли второстепенные (побочный эффект);
- варианты решения: оставить контроль / внедрить вариант / продлить тест.
Рекомендацию дать можно, но фраза «решение за вами» — обязательна. Не закрывать тест самому.

P(лучше контроля) ≥ 95% при достаточном объёме — можно предлагать закрыть в пользу варианта.
50–95% — продлить или признать разницу несущественной, тогда выбирать по простоте кода.

## Как завершать

После решения пользователя: `status: 'done'`, `winner`, `decisionNote` (дата, цифры, кто решил).
`pickVariant` начнёт отдавать победителя всем. Отдельным коммитом удалить код проигравшего
варианта и `useExperiment` из компонента, запись в реестре оставить как историю.

## Регулярная сводка

Когда пользователь просит «посмотреть метрики» — сначала `ab-report`, потом остальное:
запущенные тесты и есть главный вопрос, на который сейчас копятся данные.
