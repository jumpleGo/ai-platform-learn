# agent-refine

Создание и улучшение Claude Code subagent'ов на основе **наблюдаемых сбоев**, а не словесных оценок. Саморефлексия без галлюцинаций, over-engineering и scope creep.

## Когда использовать

- Пользователь просит создать нового subagent'а из идеи или из накопленного паттерна.
- Пользователь просит улучшить / отрефлексировать / критически пересмотреть существующего агента.
- Пользователь говорит "вынеси это в отдельного агента", "сделай из этого subagent".

## Жёсткие правила (не нарушать)

Эти правила применяются ВО ВСЕХ режимах ниже. Они важнее "красоты" результата.

**R1 — Evidence-first.** Каждое предлагаемое изменение должно ссылаться на конкретный failing case: вход, ожидание, факт. Запрещено обоснование вида "так чище / надёжнее / универсальнее". Если кейса нет — изменение не делается.

**R2 — Falsify before approve.** Перед предложением изменения сгенерируй 3 adversarial-теста:
- (a) 3 входа, которые НЕ должны триггерить агента — текущий description их ловит?
- (b) 3 входа, которые ДОЛЖНЫ триггерить агента — текущий description их пропускает?
  Изменение оправдано только если (a) или (b) показал конкретный провал.

**R3 — No hallucinated features.** Не добавляй инструкции для capabilities, которых нет в реализации. Не добавляй fallback-поведение без соответствующего tool/data source. Неуверен — помечай `[UNVERIFIED]`, не кодируй. Не ссылайся на других субагентов, если их файл не существует в `.claude/agents/` или `~/.claude/agents/`.

**R4 — Diff, not rewrite.** Изменения — минимальный diff. Если переписано больше 30% — объясни каждое удалённое предложение. Дефолтная гипотеза: существующий текст был не просто так.

**R5 — Regression check.** После предложения правок перечисли 3 поведения, которые агент обязан **сохранить**. Не можешь назвать — не понимаешь агента достаточно хорошо, чтобы его улучшать.

**R6 — Trigger monotonicity.** Расширение триггера (description) оправдано ТОЛЬКО документированной проблемой false-negatives. Сужение — ТОЛЬКО документированной проблемой false-positives. "Немного шире на всякий случай" — запрещено.

**R7 — Deletion beats addition.** При каждом проходе улучшения ищи, что можно **удалить**. Накопление инструкций деградирует качество сильнее, чем их отсутствие.

**R8 — Halt condition.** Заранее назови критерий "готово". Без него рефлексия порождает scope creep. Остановись когда критерий достигнут, даже если видишь ещё что-то "можно улучшить".

## Режим 1 — создание нового subagent'а

1. **Уточни задачу.** Спроси у пользователя: (a) 2-3 конкретных юзер-запроса, на которые агент должен делегироваться; (b) 2-3 запроса, на которые НЕ должен; (c) что агент делает в одном предложении; (d) работает ли с файлами и какими; (e) какие tools нужны (или все — inherit по умолчанию); (f) halt-condition — когда агент считает работу законченной.
2. **Не обобщай заранее.** Сначала реши одну задачу вручную в текущей сессии до успеха, ПОТОМ извлекай winning approach в системный промпт агента (iterate-then-extract). Агент, написанный "про запас" — всегда хуже.
3. **Расположение файла.**
   ```
   .claude/agents/<name>.md        # проектный, чекается в git
   ~/.claude/agents/<name>.md      # пользовательский, глобальный
   ```
   Однофайловый `.md` с YAML-frontmatter — idiomatic формат Anthropic (docs: https://code.claude.com/docs/en/subagents). Папка `<name>/AGENT.md` допустима, но встречается реже.
4. **Frontmatter-шаблон.**
   ```yaml
   ---
   name: kebab-case-name
   description: <Когда Claude должен делегировать этого агента. 1-3 предложения вида "Use when … . Do NOT use for …". Включи 5-10 конкретных триггерных формулировок на том языке, на котором говорит пользователь.>
   tools: Read, Write, Edit, Glob, Grep, Bash    # optional — без поля наследует все доступные
   model: sonnet | opus | haiku                   # optional — без поля наследует от parent
   ---
   ```
   Обязательны `name` и `description`. Description — это trigger-surface: по нему Claude решает, делегировать или нет. Формулируй про **когда использовать**, а не про "что внутри делает". Документация: https://code.claude.com/docs/en/subagents.
5. **Body — только действенные инструкции.** Свободный Markdown. Рекомендованные заголовки: "Контекст", "Принятые решения" (если есть), "Workflow / Шаги", "Жёсткие правила", "Halt-condition". Проза — только для обоснования решений, не для шагов.
6. **Самопроверка триггера.** Спроси себя, как бы спросили Claude: "When would you delegate to the <name> subagent?" Если ответ расплывчатый — description расплывчатый. Прогони R2 adversarial-тесты.

## Режим 2 — улучшение существующего агента

Строго последовательно. Не прыгай на шаг 4 без шагов 1-3.

1. **Прочитай файл целиком.** Не угадывай содержимое по имени. R3.
2. **Собери observed failures.** Откуда знаем, что агент плох? Источники в порядке предпочтения:
    - конкретные реплики пользователя из текущей или прошлой сессии;
    - логи делегаций, примеры срабатываний/несрабатываний;
    - adversarial-тесты по R2.
      Если источников нет — **не улучшай**. Сообщи пользователю: "не вижу observed failures, нечего улучшать".
3. **Классифицируй каждый failure:** `[TRIGGER]` (description ловит не то) / `[INSTRUCTION]` (body ведёт агента не туда) / `[SCOPE]` (агент делает больше/меньше чем должен) / `[FEATURE_MISSING]` (нет нужной инструкции) / `[BLOAT]` (лишние инструкции) / `[HALLUCINATION]` (ссылка на несуществующий tool/файл/агента).
4. **Предложи diff в формате** (`[CHANGE]` — цитата строк до/после или unified diff; `[REGRESSION]` — ровно 3 конкретных поведения, не абстракции):
   ```
   [CHANGE]
     - "description: Handles code review tasks."
     + "description: Use for code review of Vue/TypeScript PRs. Do NOT use for Python or design review."
   [BECAUSE] Claude делегировал этого агента в Python-PR (false positive) — общий триггер "code review" срабатывал без языкового фильтра.
   [EXPECTED] Description должен включать явный "Do NOT use for" per Anthropic best practices.
   [REGRESSION]
     1. "Отревьюй мой Vue PR" по-прежнему триггерит этого агента.
     2. "Улучши description моего агента" по-прежнему триггерит agent-refine Режим 2.
     3. "Напиши скрипт deployment" по-прежнему НЕ триггерит этого агента.
   ```
5. **Прогон R2** на новой версии: adversarial-тесты всё ещё зелёные?
6. **Strategy graveyard (опционально).** Если рядом с файлом агента существует `graveyard.md` — проверь, не пробовали ли уже. Если провал повторяется второй раз — создай файл и запиши попытку с пометкой "не работает потому что <причина>". Файл не обязателен для работы агента.

## Режим 3 — критика без правок

**Disambiguator vs Режим 2.** Если пользователь явно сказал "без правок / только ревью / только критика / не меняй" — Режим 3. Во всех остальных случаях "отрефлексируй/улучши/review" — Режим 2. При неясности спроси одной фразой: "ревью или править?"

Когда активен Режим 3 — НЕ правь. Только выдай отчёт:

```
## Strengths
- <конкретное поведение агента + почему работает>

## Observed weaknesses
- <поведение> | <вход, на котором ломается> | <что ожидалось>

## Untested areas
- <аспекты, для которых нет observed data — нельзя судить>

## Suggested experiments (не правки)
- <как получить данные, чтобы решить, надо ли править>
```

## Антипаттерны — запрещено

| Антипаттерн | Почему плохо | Что вместо |
|---|---|---|
| "Давай сделаю агента более универсальным" | Размытие триггера, over-delegation | R2, R6 |
| Переписывание всего body агента | Потеря неочевидных инвариантов | R4 |
| "Добавлю fallback на случай X" без X | Галлюцинация capability | R3 |
| Ссылка на несуществующего агента `agents/X.md` | Hallucination, R3 | Сначала проверь Glob, потом ссылайся |
| Добавление примеров "для полноты" | Раздувание контекста | R7 |
| Улучшение "по ощущениям" | Sycophancy, ICLR 2024 Huang et al. | R1 |
| Расширение scope до смежных задач | Scope creep, нарушение halt-condition | R8 |
| Description вида "Expert X that helps with Y" (что/какой) | Claude не знает КОГДА делегировать | "Use when … Do NOT use for …" (когда) |
| Агент запускает других субагентов в каждом шаге | Claude Opus склонен к over-spawning | Явный запрет в body |

## Взаимодействие с правилами базового контекста

Skill усиливает, а не обходит правила из system prompt:
- "Don't add features / refactor / abstractions beyond task" → R3, R7, R8.
- "Don't add error handling for scenarios that can't happen" → R3.
- "Default to no comments / no docs unless asked" → применяется к генерируемым файлам агентов.
- "Edit existing files over creating new ones" → Режим 2 приоритетнее Режима 1, если файл уже есть.
- "Trust but verify" → R1, R2 (читай файл до того, как критикуешь).

Если правило базового контекста конфликтует с правилом отсюда — побеждает базовое.

## Halt-check перед выдачей результата

Перед отправкой ответа пользователю ответь себе:
1. Каждое изменение имеет `[BECAUSE]` с конкретным входом? Если нет — удали изменение.
2. Есть ли `[REGRESSION]`-список? Если нет — добавь или удали изменение.
3. Я добавил что-то, что не было явно запрошено? Если да — удали.
4. Description тратит слова на "что" вместо "когда"? Перепиши.
5. Я сослался на файл/tool/агента, который не проверял что существует? Проверь или удали ссылку.
6. Критерий "готово" достигнут? Если да — стоп, даже если видишь ещё что-то.
